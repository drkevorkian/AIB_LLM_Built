# ADR 0023: Versioned workspace artifacts and opposite themes

Status: Development candidate for v0.22.0. Extends ADRs 0002/0005/0008/0022.

## Original bytes and authority

Artifacts belong to one local workspace. Upload is an explicit human action and never invokes a provider or consumes a turn. The authenticated upload command carries a reviewed room revision, client UUID, filename, supported media type and canonical base64 bytes. An optional artifact ID creates a new immutable version of that workspace's existing artifact; a new upload creates a new artifact ID. Server-owned version IDs, ordinal versions, raw-byte SHA-256, byte size, timestamp and original filename provide provenance. Each workspace retains at most 40 total versions and 8 MiB of original bytes; a version is at most 512 KiB. Zero-byte originals are permitted. Repeated identical upload UUIDs are inert; changed content, stale reviews and cross-workspace identities fail atomically. Pending model work can continue with its submitted versions; uploads never rewrite it. Archives permit reading but reject uploads.

SQLite schema 3 adds a private BLOB table referencing workspace rows with foreign-key cascade deletion. Metadata and bytes commit in the same room transaction. Room JSON, events, audits and automatic list reads never contain original bytes. Upgrade from schemas 1/2 is additive, keeps existing data and the writer lease, and rejects newer schemas. Whole-workspace and bulk workspace deletion commit removal of metadata/bytes before transport cancellation. Thread deletion retains workspace-owned originals but removes message grants and copied context belonging to deleted source messages. Logical deletion does not promise forensic erasure or retraction of provider submissions/exports.

Read/preview/original routes authenticate the same local session/Host/Origin boundary and check exact workspace/version membership before fetching bytes. A missing/corrupt byte record, changed hash, size or metadata fails closed. Original downloads use application/octet-stream, attachment disposition, nosniff and no-store; user filenames never become filesystem paths or executable navigation. There is no server filesystem extraction or overwrite.

## Validation and safe previews

Supported media are UTF-8 plain text, Markdown and JSON; PNG/JPEG; PDF; ZIP; and opaque binary. Validate filename length, control characters, separators, Windows reserved names and trailing dots/spaces. Validate canonical base64, byte limits, strict UTF-8/control characters, JSON syntax and appropriate binary signatures. Text previews render exact bounded escaped text, with an explicit omission notice above 16,000 characters; full bytes remain available. Images, PDFs and opaque files have metadata previews and explicit original downloads, with no embedded viewers, image decoding, scripts, remote loads or inferred content. ZIP previews show only a validated attributed manifest.

ZIP validation supports single-disk classic stored/deflated regular files, bounded to 32 members, 512 KiB per member, 4 MiB total inflated bytes and a 100:1 ratio per member. Validate actual inflation lengths/CRC, complete deflate consumption, central/local names/methods/flags/bounds, bounded extra fields and nonoverlapping record layout. Reject encrypted/ZIP64/split/self-extracting/data-descriptor archives, symlinks/special files, unsafe/duplicate paths, alternate Unicode path fields, unsupported flags/methods and nested archive filenames/signatures. No members are written to disk or recursively expanded. Format references: [PKWARE APPNOTE](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT) and [Node zlib](https://nodejs.org/api/zlib.html); the implementation is an application-owned bounded reader, not a general archive utility.

## Explicit provider selection and frozen versions

Only an explicit human Question, relay or discussion root may select up to four retained UTF-8 text versions. Updates/interjections reject selection; binary/ZIP/image/PDF inclusion is visibly unsupported and rejected before message/turn/provider work. Uploading, previewing, downloading, model prose, an old message or a summary never grants inclusion. The composer identifies selected filenames/version/hash and actual recipient provider/model bindings. Selected full text must fit 16,000 characters each and the existing complete context/model limits; no attachment text is silently truncated. Provider envelopes carry selected artifacts as untrusted attributed user data, never system instructions, tools, routing or automatic source retrieval. Native binary provider capabilities remain separate original requirements.

The human message and frozen snapshot retain exact version references, hashes, metadata and the granting source message ID. Snapshots separately copy selected full text; original retries, synthesis revisions, relay/discussion/peer/correction continuations use that exact copy. A newer artifact version cannot enter an existing invocation. All five native text adapters use the common data envelope; credentials/model generation are not used in verification. Per-model budgets include artifact data and cannot trim it. Deleting a granting thread cancels/redacts copied grants in surviving contexts and blocks affected retries. Workspace-owned bytes remain available independently until workspace deletion.

Upload/source requests are bounded. Stale or unknown upload acknowledgements require explicit Refresh to inspect the UUID and current metadata; no automatic replay. Composer/upload drafts survive other views, previews, failures and theme changes. Refresh does not silently replace selected version IDs with newer versions. Inspection/export disclose exact recorded artifact references without pretending metadata-only files reached a provider. Artifact manifest export/import, merge/conflict review, execution, restricted multi-user ACL and native binary provider integration remain separate unchecked work.

## Opposite browser palettes

Settings preserves Dark and Light and adds Ghost White and Blizzard Blue. Ghost White uses #F8F8FF surfaces, black text and #ACE5EE lines. Blizzard Blue uses black surfaces, #ACE5EE text and #F8F8FF lines. The header toggle swaps the active pair (Dark/Light or Ghost White/Blizzard Blue). Browser preference persists without room mutations, provider work or draft changes; invalid/unavailable stored preferences fall back safely and failed writes disclose non-persistence. Corners retain the existing square/0–4px policy. Broader application accessibility/contrast audits remain open.

## Required evidence

Meaningful source/service/browser checks must cover immutable raw bytes/hashes/version references, strict filename/media/archive limits, corrupt/foreign reads, UUID/stale/database failures, real SQLite migration/restart/deletion, protected fitting and frozen sibling/retry/workflow bindings, authenticated downloads/previews, harmless hostile text, lost upload acknowledgements, draft retention, both new palette colors/persistence and narrow layouts. Complete all six CI jobs and both Ubuntu browser suites before checking the five original section 13 requirements. No license grant, npm publication, model credential or version 1 release is included.
