# v0.4.0 — Settings and workspace management

Open **Settings** in the header to change app defaults, edit the selected workspace, and configure its participants. Workspace and thread trash buttons now offer named confirmations and cancellation. These changes extend the working discussion/relay application from v0.3.0.

## Changes

- Add a directly addressable Settings page with theme, saved creation/composer defaults, workspace name/objective/turn limit, and participant/model controls.
- Preserve open composer drafts while visiting Settings; apply new defaults to new workspaces/composers. Keep API keys in the service environment.
- Delete workspaces with their participants/history and abort active requests/probes. Preserve other workspaces and update all open views.
- Delete threads with their requests, attempts, workflows, and context copies. Cancel dependent work, identify redacted historical snapshots, and reject retries using deleted context.
- Keep consumed turn usage and monotonic message sequence numbers; release unused reservations and reject delayed replay of deleted human commands.
- Provide an empty app after deleting the final workspace, including after service restart, with creation and Settings still available.
- Additively migrate the SQLite database from v1 to v2 for separate persisted defaults and one-time welcome initialization. Existing room records remain readable.

## Verification

99 engine/service/provider-protocol tests and 12 Chromium UI tests pass. Strict TypeScript checks, formatting, a production build, and the production dependency audit pass. Browser tests exercise the production service, including confirmed deletion, two open views, settings persistence, preserved drafts, narrow layouts, and an actual service restart after deleting the final workspace. Source CI runs on Linux, Windows, and macOS; Chromium tests run on Linux.

## Limits

In the current UI one workspace is one conversation room. Multi-room workspace groups, archive/restore, bulk management, thread renaming, and backup/retention tools remain planned. Deletion is permanent in active app records but does not promise forensic disk erasure or retract provider submissions, exported files, external backups, or material incorporated into surviving answers. Aborting a local request cannot guarantee remote cancellation or refunded billing.

New defaults do not retroactively change existing workspaces or open composer settings. Workspace/participant edits require pending work to finish or be stopped. Live account/model smoke tests, browser-session transport, and graphical OS-backed credential storage remain unverified or unimplemented as recorded in the README's complete TODO list.
