# v0.5.0 — Participant rosters and configuration history

Create a workspace with 1–8 participants, then use **Settings → Participants & connections** to add, deactivate, or reactivate identities. The three-participant welcome workspace still works as before. Renaming or changing a participant now records its full configuration history while older answers retain their original attribution.

## Changes

- Support single-participant and larger workspaces in directed questions, parallel collection/synthesis, relays, and bounded discussions.
- Add participants in simulation without invoking a provider; configure live connections explicitly. Keep independent identities even when names and provider/model settings repeat.
- Preserve messages, settings, revisions, and consumed usage when deactivating. Require at least one active participant and count inactive identities toward the eight-identity cap.
- Enforce active-only recipients, synthesizers, relay steps, coordinators, and frozen peer grants. Reject roster changes while jobs, unfinished workflows, or workspace connection probes remain.
- Reconcile roster updates in other open views without losing draft text. Remove inactive selections, adjust quorum, and keep additions/reactivations as observers until selected.
- Record all new configuration revisions, including unused edits and activation changes, and expose history in Settings. Recover known legacy configurations while disclosing unknown edit times.
- Preserve historical author names in messages, workflow labels, source context, and Markdown export. Distinguish duplicate names in recipient controls while routing by stable IDs.
- Require reactivation before retrying a workflow with inactive dependencies. Preserve original model, objective, and roster bindings when retrying synthesis after settings change.

## Upgrade

Stop the local service, update the checkout, install locked dependencies, and rebuild:

```sh
git pull --ff-only
npm ci
npm run build
npm start
```

Continue using Node 26.10 or newer in the 26.x series, or Node 24.15 or newer in the 24.x series. Existing rooms remain readable; no database schema change is required. Missing activation flags mean active. Legacy configuration history is recovered from stored snapshots and current settings; unused revisions that earlier versions never recorded cannot be recreated. New edits retain full revisions from this version onward. Interrupted work retains the existing explicit recovery behavior.

## Limits

Roster/configuration edits require pending work to finish or be stopped. Participant removal, rosters above eight identities, and membership changes during active workflows remain planned. Deactivation controls new invocations and does not make messages private or remove historical context. The global four-generation limit still applies. Browser-session transports, automatic network retries, remote provider reconciliation, attachments, and graphical credential management remain outside this release.

See [ADR 0006](../architecture/0006-participant-rosters.md) for the roster, history, and retry contracts, and the complete checklist at the end of [README.md](../../README.md) for remaining work.
